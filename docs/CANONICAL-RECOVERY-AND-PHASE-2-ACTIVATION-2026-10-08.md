## 5. Avatar State — non-negotiable contract
Visible board names remain:
- **A Cast Board**
- **Character Detail Specifications Board**
- **360 View Board**

Profiles:
- **32-view master** — canonical default for new characters and material identity/physical changes.
- **16-view state** — economical default for wardrobe-only or limited non-identity changes.
- **24-view** — archived/intermediate study, not canonical full coverage.
- **64-slot full-height profile** — 8 directions × 8 configured heights. It is an expansion profile; exact eight camera heights remain a calibration requirement.

Identity rules:
- approved visual reference outranks descriptive shorthand;
- no prompt may silently alter a locked identity anchor;
- locked boards are versioned, never silently overwritten;
- scene records pin exact approved versions;
- new masters do not rewrite prior locked scenes;
- voice and performance version independently from appearance;
- generated/saved/approved/locked are distinct lifecycle states;
- rejected and superseded outputs remain in history.

Required runtime proof:
- signed-in save/reload;
- exact avatar retrieval;
- Character Detail linkage;
- coverage-set linkage;
- voice persistence;
- appearance/state-difference persistence;
- Cast Board assignment;
- multi-character retrieval;

- history/audit/provenance record.

## 6. World State / Scene Dissection
A scene is a persistent world volume, not a regenerated flat background.

Persist:
- geography and zones;
- visible entities;
- off-screen entities;
- acoustic sources;
- avatar position/perception/reaction;
- camera position/orientation/movement;
- weather, wind, rain, light, shadow and reflections;
- environmental physics;
- object state and interactions;
- causality and aftermath;
- temporal continuity;
- uncertainty/confidence and evidence.

Causal chain:
**world geometry → weather/light → environmental physics → event/object movement → sound propagation → avatar perception → avatar reaction → camera response → continuity update**

Unknown unseen sources stay unknown. Example: an audible horn is not silently converted into a truck.

## 10. Automation architecture
Canonical workflow:
**Intake → Plan → Decompose → Prepare Assets → Route Provider → Execute → Record Output → QC/Review → Revise/Approve → Package → Distribute/Hand Off → Archive/Audit**

THELMA is the operations/orchestration layer. Specialists remain role-bound:
- THELMA — orchestration/routing;
- H.E.N.R.Y. — architecture/root cause;
- P.E.R.C.Y. — security;
- V.E.R.I.T.A.S. — evidence/verification;
- The Auditor — quality/release;
- Canon Keeper — canon/memory;
- L.I.L.Y. — guidance/training.

Automation may inspect, route, propose, generate work packets and run permitted production steps. It does **not** gain new destructive, publishing, spending, credential, legal or approval authority merely because a workflow is automated.

## 11. Automation gates
No autonomous step may cross these boundaries without the applicable existing authority:
- identity/master approval;
- key-frame approval before motion where the production standard requires it;
- rights/provenance exceptions;
- material continuity exception;
- final release certification;
- external publishing;
- financial spend/contract action;
- credentials/security changes;
- destructive data changes.

A provider task finishing is not an approval.

## 12. Data / evidence requirements
Every production artifact should be traceable through:
- stable asset ID;
- immutable version;
- checksum where supported;
- project/scene/shot/state relation;
- avatar/world state versions;
- source/provenance;
- provider/model/task record;
- prompt/config version where applicable;
- QC result;
- approval decision;
- supersession lineage;
- cost/usage attribution;
- audit correlation ID.

Truth states remain explicit: LIVE only when currently verified; otherwise use states such as Recorded, Available, Degraded, Pending Verification, Not Connected or Export Only.
